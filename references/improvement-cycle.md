# 개선 사이클 — 선순환 구조

이 레포는 **쓰면서 좋아지는** 구조로 설계되어 있습니다.
에이전트 운영이 계속 발전할 수 있게 만드는 워크플로우입니다.

## 선순환이 도는 방식

```
우리가 쓴다 (도그푸딩)
  → 개선점 발견
    → 보안 검사 (자동)
      → 발행 (bin/publish.py)
        → 다른 사람이 쓴다
          → Issues로 피드백 (자발적)
            → 반영 → 다시 발행
              → 반복
```

## 데이터는 어떻게 모이나요?

선순환이 돌려면 "뭐가 좋아졌는지"를 아는 데이터가 필요합니다.
데이터는 두 경로로 모입니다:

| 경로 | 내용 | 방식 |
|---|---|---|
| **우리의 도그푸딩** | 매일 쓰면서 발견한 불편·개선점 | 우리가 직접 `publish.py`로 발행 |
| **외부 사용자의 피드백** | 버그 신고·개선 요청·사용 후기 | GitHub Issues (자발적 공유만) |

> **자동 수집은 하지 않습니다.** public 레포라서 다른 사람의 사용 데이터를
> 몰래 모을 수 없고, 모아서도 안 됩니다. 공유하고 싶은 사람만 Issues에 남깁니다.

## 개선 요청 경로

1. **채팅으로 직접** — Muse에게 "muse-agent-ops에 이거 반영해줘"라고 말하면
   그 자리에서 수정 → `publish.py`로 보안 검사 → push까지 처리됩니다.
2. **이슈로 등록** — GitHub Issues에서 `버그 신고` / `개선 요청` 템플릿으로 남기면
   다음 작업 시점에 반영됩니다.

## 발행 프로세스 (`bin/publish.py`)

```
요청 접수 → 내용 검토 → 수정 → 보안 검사 → push → CHANGELOG 기록
```

보안 검사는 우회할 수 없습니다:

1. **`secret-scan.py`** — 토큰·키·비밀값 패턴 감지
2. **공개 안전성 체크** — 이메일·사설 IP·내부 도메인·개인정보 패턴 감지
3. 하나라도 걸리면 **push 중단**

- 작은 수정(문서 오타·라벨 색상 등)은 바로 반영
- 동작이 바뀌는 수정(스크립트 로직 등)은 dry-run으로 먼저 검증 후 반영
- 보안 관련 수정은 `references/secret-policy.md` 기준으로 검토

## 버전 관리

- `VERSION` 파일에 현재 버전을 명시합니다.
- 기능 단위로 커밋합니다. 커밋 메시지는 한국어로, 무엇을 바꿨는지 명확히.
- 바뀐 내용은 `CHANGELOG.md`에 기록합니다. 기여자가 있으면 함께 남깁니다.
- 스크립트 동작이 바뀌면 관련 가이드 문서도 함께 고칩니다.

## 다른 곳에서도 동일하게

이 레포는 **어디서 쓰든 똑같이 동작**하도록 설계되어 있습니다:

- **의존성 없음** — Python 표준 라이브러리만 씁니다 (pip install 불필요)
- **멱등성** — `setup.py`를 여러 번 돌려도 같은 결과 (이미 있으면 건너뜀)
- **nlook 없이 동작** — 문서 백엔드는 로컬 파일로 시작 가능
- **버전 명시** — `VERSION` 파일로 "내가 쓰는 게 최신인지" 확인 가능

## 스케줄러를 두지 않는 이유

이 레포는 이슈 발생 빈도가 낮습니다. 별도 감시 스케줄러를 두는 대신,
요청이 들어오면 그때 처리하는 온디맨드 방식으로 운영합니다.
(Muse 채팅에서 바로 처리 가능)
