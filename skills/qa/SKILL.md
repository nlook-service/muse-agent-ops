# qa — 도그푸딩 QA 스킬

## Purpose
테스터가 아니라 **실제 고객의 눈**으로 서비스를 쓰고, 문제를 찾으면
"어디에서" 생긴 것인지 정확히 특정해서 이슈로 남긴다.

## Workflow

### 1. 고객처럼 탐색하기
- 목적을 가진 고객으로 행동한다. 예: "메모를 예쁘게 정리하고 싶다"
- 정해진 시나리오가 아니라 스스로 판단해서 앱 전체를 꼼꼼히 탐색한다
- 테스트용 데이터는 표시를 남긴다 (예: 제목에 '도그푸딩')

### 2. 체크포인트
자세한 체크리스트는 `references/checklist.md`.
핵심 8개: 한글 카피 / 영문 카피 / 디자인 느낌 / 가독성 / 퍼포먼스 / UI·UX 느낌 / 사용성 / 차별점

### 3. 이슈 등록 — 위치 특정 엄수
아래 4개 중 **하나라도 빠지면 이슈 등록 금지**:

1. **페이지 URL 전체** (예: `https://nlook.me/documents/xxx`)
2. **메뉴 경로** (예: 내 글 > 목록 > 3번째 글)
3. **화면명 + 문제 부위** (예: 글 읽기 화면 우측 상단 공유 버튼 옆)
4. **문제 부위가 보이는 스크린샷**

"설정 화면에서 이상함" 같은 막연한 표현 금지.
재현 절차의 각 단계마다 "어디서 무엇을 눌렀다"가 드러나야 한다.

본문 항목: 테스트 계정 ID · 환경(브라우저·OS·화면 크기) · 재현 절차(번호) ·
기대 결과/실제 결과 구분 · 심각도(치명/높음/중간/낮음)

제목 형식: `[영역] 간결한 문제 설명`
템플릿: `assets/issue-template.md`

### 4. 보고
- 1인칭 고객 시점으로 서술: "무엇을 기대하고 클릭했는데 → 실제로 어떻게 됐고 → 어떤 기분이었는지"
- 좋았던 점도 1가지 이상 ("왜 좋았는지" 체감 위주로)
- 등록한 이슈 목록 (URL 포함)

## Operating Rules
1. 추측성 문제(원인 미검증)는 이슈로 만들지 말고 리포트에 '검증 불가'로 기록
2. 기존 open 이슈와 중복 확인 후 신규만 등록
3. 유료 결제·실제 공개 발행 등 되돌리기 어려운 행동 금지
4. 테스트 계정과 개인 계정을 절대 혼용하지 않는다
